5.4 Booking concurrency and data integrity (WeAce)
Problem
	Two users trying to book the same slot (for example 2 to 3 pm on a coach's calendar) at the same moment could create a double booking.
	Solution
	The system checks real-time free slots, and the booking is created inside a database transaction, with a check at insert time that the coach calendar is still free. ACID transactions and optimistic locking handle parallel bookings.
	Explain clearly
	Atomicity, Consistency, Isolation, Durability. Optimistic locking: a version field must be unchanged for the update to succeed, otherwise the second request fails cleanly. Pessimistic locking (SELECT FOR UPDATE) is the alternative. A unique constraint is a last line of defense. Idempotency keys make retries safe.
	Result
	No double bookings under parallel requests. [CONFIRM and add numbers if known.]
